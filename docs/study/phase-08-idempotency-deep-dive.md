# 멱등성(Idempotency) 완전 정복 — 키 생성, 훅, 동작 원리

---

## 1. 먼저 정리: 멱등성 키와 IdempotencyRecord의 관계

### 질문에 대한 답

> "IdempotencyRecord는 주문하기를 누를 시 order 데이터에 등록되고,
> 결제작업을 한번 했을 시 여러 번 결제작업이 안 되도록 조회해서 확인하는 수단"

**반만 맞다.** 현재 프로젝트에는 멱등성 키가 **두 군데**에 사용된다:

```
┌─────────────────────────────────────────────────────────────────┐
│                    멱등성 키가 사용되는 2곳                       │
├──────────────────────────┬──────────────────────────────────────┤
│  ① Order.idempotencyKey  │  ② IdempotencyRecord 테이블          │
│  (주문 테이블의 컬럼)      │  (미들웨어가 관리하는 별도 테이블)     │
├──────────────────────────┼──────────────────────────────────────┤
│  용도: 주문 데이터에 키를  │  용도: HTTP 응답 전체를 캐싱해서       │
│  기록해두는 것            │  같은 요청이 오면 핸들러 실행 없이      │
│  (현재 Phase 3~7에서 사용) │  저장된 응답을 그대로 반환            │
│                          │  (Phase 8에서 구현 예정)              │
│  위치: schema.prisma의    │  위치: schema.prisma의               │
│  Order 모델 필드          │  IdempotencyRecord 모델              │
│                          │                                      │
│  현재 상태:               │  현재 상태:                           │
│  Order 생성 시 키 저장됨   │  모델만 정의, 미들웨어 미구현          │
│  BUT 중복 체크는 안 함     │  Phase 8에서 미들웨어 구현 예정        │
└──────────────────────────┴──────────────────────────────────────┘
```

### 현재 코드의 문제점

현재 `order_service.py`를 보면:

```python
# order_service.py 35번째 줄
order = await self.db.order.create(
    data={
        "idempotencyKey": idempotency_key,  # ← 단순히 저장만 함
        ...
    }
)
```

키를 **저장만** 하고, "이 키로 이미 주문이 있는지" **확인하지 않는다.**
`Order.idempotencyKey`에 `@unique` 제약이 있어서 DB 레벨에서 중복 INSERT는 에러가 나지만,
그걸 잡아서 "기존 주문을 반환"하는 로직은 없다.

### Phase 8에서 추가되는 것: IdempotencyMiddleware

```
Phase 8 이후의 완전한 멱등성 보장 흐름:

                      프론트엔드                     백엔드
                      ─────────                     ──────
                      generateIdempotencyKey()
                        │
                        │ "pos_a1b2_1707900000_x8k2"
                        │
                        ▼
                      POST /api/orders
                      Header: Idempotency-Key: pos_a1b2_...
                      Body: { idempotency_key: pos_a1b2_..., items: [...] }
                        │
                        │                    ┌──────────────────────────┐
                        │                    │ IdempotencyMiddleware    │
                        │                    │                          │
                        ▼                    │ 1. 헤더에서 키 추출       │
                                             │ 2. IdempotencyRecord에서 │
                                             │    키로 조회              │
                                             │                          │
                                             │  ┌─ 키가 없음 ──────────┐│
                                             │  │ 핸들러 실행 (주문 생성) ││
                                             │  │ Order 테이블에 키 저장  ││
                                             │  │ 응답을 IdempotencyRecord││
                                             │  │ 에도 저장 (캐싱)       ││
                                             │  └──────────────────────┘│
                                             │                          │
                                             │  ┌─ 키가 있음 (미만료) ──┐│
                                             │  │ 핸들러 실행 안 함!     ││
                                             │  │ 저장된 응답 그대로 반환 ││
                                             │  └──────────────────────┘│
                                             └──────────────────────────┘
```

**핵심 차이:**

|               | Order.idempotencyKey      | IdempotencyRecord            |
| ------------- | ------------------------- | ---------------------------- |
| **역할**      | 주문에 키를 기록 (데이터) | HTTP 응답을 캐싱 (중복 방지) |
| **중복 체크** | DB unique 제약만 (에러)   | 미들웨어가 저장된 응답 반환  |
| **범위**      | 주문 생성만               | 모든 POST/PATCH 요청         |
| **결과**      | 키 중복 시 DB 에러        | 키 중복 시 성공 응답 재반환  |

## 2. generateIdempotencyKey — 동작 원리

### 코드가 하는 일: 한 문장 요약

> **장바구니 내용을 해시하고, 현재 시각과 랜덤값을 붙여서, 고유한 문자열 키를 만든다.**

### 구체적인 상황 예시

```
╔═══════════════════════════════════════════════════════════════════╗
║  상황: 고객이 아메리카노 2잔 + 카페라떼 1잔을 주문                  ║
╚═══════════════════════════════════════════════════════════════════╝

장바구니 상태:
┌──────────────────────────────────┐
│  아메리카노 (id: menu_abc) × 2   │
│  카페라떼   (id: menu_def) × 1   │
└──────────────────────────────────┘

items 배열:
  [
    { menuId: "menu_abc", quantity: 2 },
    { menuId: "menu_def", quantity: 1 }
  ]


Step 1: 직렬화 + 정렬
─────────────────────

  items.map(i => `${i.menuId}:${i.quantity}`)
    → ["menu_abc:2", "menu_def:1"]

  .sort()
    → ["menu_abc:2", "menu_def:1"]  (알파벳순 정렬)
                                     ※ 순서가 달라도 같은 결과를 보장

  .join("|")
    → "menu_abc:2|menu_def:1"       ← payload


Step 2: djb2 해시
─────────────────

  simpleHash("menu_abc:2|menu_def:1")

  내부 동작:
    hash = 5381
    'm' → hash = (5381 × 33) ^ 109 = 177580
    'e' → hash = (177580 × 33) ^ 101 = 5860241
    'n' → hash = (5860241 × 33) ^ 110 = 193387963
    ... (나머지 문자들도 반복)
    최종 → hash >>> 0 → 양수 변환
    → .toString(36) → "a1b2c3"      ← 36진수 문자열


Step 3: 타임스탬프
──────────────────

  Math.floor(Date.now() / 1000)
  = Math.floor(1707900000000 / 1000)
  = 1707900000                       ← 초 단위 유닉스 시간


Step 4: 랜덤값
──────────────

  crypto.randomUUID().slice(0, 8)
  = "a1b2c3d4-e5f6-...".slice(0, 8)
  = "a1b2c3d4"                       ← UUID 앞 8자리


Step 5: 조합
────────────

  `pos_${hash}_${timestamp}_${random}`
  = "pos_a1b2c3_1707900000_a1b2c3d4"
     │    │         │          │
     │    │         │          └── 충돌 방지 (랜덤)
     │    │         └── 시간 순서 보장
     │    └── 장바구니 내용 핑거프린트
     └── 출처 구분 (POS)
```

### 같은 장바구니, 다른 시점 → 다른 키

```
10:30에 주문:  "pos_a1b2c3_1707900000_x8k2m4n7"
10:31에 같은 주문:  "pos_a1b2c3_1707900060_p3q9r1s5"
                         │          │          │
                    해시 같음   시간 다름   랜덤 다름
                    (같은 메뉴)

→ 다른 키 → 서로 다른 주문으로 처리됨 ✓
  (의도적으로 같은 걸 다시 주문하는 것이므로 정상)
```

### 네트워크 재시도 시 → 같은 키 유지 (useIdempotencyKey 훅의 역할)

```
10:30:00 첫 번째 시도: "pos_a1b2c3_1707900000_x8k2m4n7"  ← getKey()가 생성
10:30:03 재시도:       "pos_a1b2c3_1707900000_x8k2m4n7"  ← getKey()가 같은 키 반환
10:30:05 또 재시도:    "pos_a1b2c3_1707900000_x8k2m4n7"  ← 여전히 같은 키

→ 서버: "아, 이 키 이미 처리했네" → 저장된 응답 반환 (중복 주문 방지 ✓)

10:35:00 새로운 주문: reset() 호출 → keyRef.current = null
         getKey() → "pos_a1b2c3_1707900300_j7k8l9m0"  ← 새 키 생성
```

## 3. useIdempotencyKey 훅 — 왜 useRef인가?

### 이 훅이 해결하는 문제

```
╔═══════════════════════════════════════════════════════════════════╗
║  문제: 결제 플로우 중에 키가 바뀌면 안 된다                                 ║
║                                                                   ║
║  결제하기 클릭 → POST /api/orders (키: abc) → 응답 대기 중...            ║
║                                                                   ║
║  이 사이에 리렌더링이 일어나면?                                          ║
║  (예: 장바구니 비우기, 상태 업데이트 등)                                   ║
║                                                                   ║
║  키가 바뀌면: POST 재시도 시 다른 키 → 중복 주문 발생 ✗                     ║
║  키가 유지되면: POST 재시도 시 같은 키 → 서버가 캐시 반환 ✓                  ║.
╚═══════════════════════════════════════════════════════════════════╝
```

### 후보 1: useState — 탈락 이유

**useState의 특징:**

- 값이 변경되면 **컴포넌트가 리렌더링**된다
- 리렌더링마다 새로운 렌더 사이클이 실행된다
- 상태 업데이트는 **비동기**로 처리될 수 있다 (배칭)

```
useState를 사용한 경우:

function useIdempotencyKey(items) {
  const [key, setKey] = useState<string | null>(null);  // ← useState

  const getKey = () => {
    if (!key) {
      const newKey = generateIdempotencyKey(items);
      setKey(newKey);      // ← 상태 업데이트 → 리렌더링 트리거!
      return newKey;
    }
    return key;
  };

  const reset = () => setKey(null);  // ← 리렌더링 트리거!

  return { getKey, reset };
}


타임라인:
─────────────────────────────────────────────────────────

시점 1: 고객이 "결제하기" 클릭
        │
        ▼
     getKey() 호출
        │
        ├── key === null → 새 키 생성: "pos_abc_123_xyz"
        ├── setKey("pos_abc_123_xyz")
        │       │
        │       └── ⚡ 리렌더링 트리거됨!
        │           Cart 컴포넌트 전체가 다시 렌더링
        │           (장바구니 UI, 버튼, 금액 표시 모두)
        │
        └── return "pos_abc_123_xyz"

시점 2: POST /api/orders 요청 출발
        Header: Idempotency-Key: pos_abc_123_xyz

시점 3: 리렌더링 실행됨 (setKey 때문에)
        │
        └── 불필요한 렌더링 발생 ✗
            UI가 깜빡이거나 성능 저하 가능

시점 4: 응답 수신 → 성공 → reset() 호출
        │
        ├── setKey(null)
        │       │
        │       └── ⚡ 또 리렌더링!
        │
        └── 총 2번의 불필요한 리렌더링 발생


문제점 정리:
┌───────────────────────────────────────────────────┐
│ 1. 키 생성/삭제마다 리렌더링 → 성능 낭비           │
│ 2. 키는 UI에 표시되지 않음 → 리렌더링 자체가 불필요 │
│ 3. 결제 중 리렌더링 → 사용자가 "깜빡임" 경험 가능   │
│                                                   │
│ 결론: 탈락 ✗                                       │
└───────────────────────────────────────────────────┘
```

### 후보 2: useMemo — 탈락 이유

**useMemo의 특징:**

- 의존성 배열이 변경될 때만 값을 **재계산**한다
- 의존성이 안 바뀌면 이전 값을 **캐시**해서 반환한다
- 리렌더링마다 의존성을 **비교**한다

```
useMemo를 사용한 경우:

function useIdempotencyKey(items) {
  const key = useMemo(                    // ← useMemo
    () => generateIdempotencyKey(items),
    [items]                               // ← 의존성: items
  );

  // 문제: reset()을 구현할 방법이 없다!
  // useMemo는 "의존성이 바뀌면 재계산"이지,
  // "내가 원할 때 재계산"이 아니다.

  return { key };
}


타임라인:
─────────────────────────────────────────────────────────

시점 1: 컴포넌트 마운트
        items = [{ menuId: "abc", quantity: 2 }]
        │
        ▼
     useMemo 실행
        → key = "pos_abc_123_xyz"

시점 2: 고객이 장바구니에 메뉴 추가
        items = [{ menuId: "abc", quantity: 2 }, { menuId: "def", quantity: 1 }]
        │
        ▼
     items가 변경됨 → useMemo 재계산!
        → key = "pos_def_456_uvw"  ← ⚡ 키가 바뀜!

시점 3: 이전 키("pos_abc_123_xyz")로 보낸 요청이 아직 진행 중인데
        새 키가 되어버림

        재시도 시: 새 키("pos_def_456_uvw")로 요청
        → 서버: "이 키 처음 봄" → 주문을 또 생성! ✗ 중복 주문!


문제점 정리:
┌───────────────────────────────────────────────────────────┐
│ 1. items가 바뀌면 키가 자동으로 바뀜                             │
│    → 결제 진행 중에 장바구니 변경(CLEAR) 시 키가 달라짐             │
│    → 재시도 시 서버가 새 요청으로 인식 → 멱등성 깨짐 ✗               │
│                                                           │
│ 2. reset() 구현 불가능                                      │
│    → useMemo는 "의존성 기반 자동 재계산"이지                     │
│    → "내가 원할 때 초기화"가 아님                               │
│    → 새 주문을 시작할 때 명시적으로 키를 리셋할 수 없음               │
│                                                           │
│ 3. 리렌더링마다 items 참조 비교                                 │
│    → 배열은 매번 새 참조 → 매번 재계산 가능성                      │
│    (React Compiler가 해결해줄 수도 있지만 보장은 못 함)            │
│                                                           │
│ 결론: 탈락 ✗                                               │
└───────────────────────────────────────────────────────────┘
```

### 최종 선택: useRef — 채택 이유

**useRef의 특징:**

- `.current`에 아무 값이나 저장 가능한 **변경 가능한 박스**
- `.current`를 변경해도 **리렌더링이 발생하지 않는다**
- 컴포넌트의 전체 생명주기 동안 **동일한 ref 객체를 유지**한다
- 명시적으로 `.current`를 읽고 쓸 수 있다

```
useRef를 사용한 경우 (현재 구현):

function useIdempotencyKey(items) {
  const keyRef = useRef<string | null>(null);  // ← useRef

  const getKey = () => {
    if (!keyRef.current) {
      keyRef.current = generateIdempotencyKey(items);  // 직접 할당
    }
    return keyRef.current;
  };

  const reset = () => {
    keyRef.current = null;  // 직접 할당 → 리렌더링 없음
  };

  return { getKey, reset };
}


타임라인 (정상 플로우):
─────────────────────────────────────────────────────────

시점 1: 고객이 "결제하기" 클릭
        │
        ▼
     getKey() 호출
        │
        ├── keyRef.current === null
        ├── keyRef.current = "pos_abc_123_xyz"  ← 직접 할당
        │       │
        │       └── 리렌더링 없음! ref 변경은 React가 모름
        │
        └── return "pos_abc_123_xyz"

시점 2: POST /api/orders 요청 출발
        Header: Idempotency-Key: pos_abc_123_xyz

시점 3: 장바구니 CLEAR (dispatch({ type: "CLEAR" }))
        → Cart 리렌더링 발생
        → 하지만 keyRef.current = "pos_abc_123_xyz"  ← 그대로 유지!

시점 4: 네트워크 에러 → 재시도
        │
        ▼
     getKey() 호출
        │
        ├── keyRef.current === "pos_abc_123_xyz"  ← null이 아님
        │
        └── return "pos_abc_123_xyz"  ← 동일한 키 반환! ✓

시점 5: 재시도 요청
        Header: Idempotency-Key: pos_abc_123_xyz  ← 같은 키
        → 서버: "이 키 이미 처리함" → 저장된 응답 반환 ✓

시점 6: 결제 성공 → 새 주문 준비
        │
        ▼
     reset() 호출
        │
        ├── keyRef.current = null  ← 초기화
        │       │
        │       └── 리렌더링 없음!
        │
        └── 다음 getKey() 호출 시 새 키 생성


성공 포인트 정리:
┌───────────────────────────────────────────────────────────┐
│ 1. 키 생성/변경 시 리렌더링 없음 → 성능 최적 ✓             │
│ 2. 장바구니가 변경되어도(CLEAR) 키 유지 → 멱등성 보장 ✓     │
│ 3. reset()으로 명시적 초기화 가능 → 새 주문 시작 제어 ✓     │
│ 4. 리렌더링과 무관하게 동일 ref 객체 유지 → 안정적 ✓        │
│                                                           │
│ 결론: 채택 ✓                                               │
└───────────────────────────────────────────────────────────┘
```

## 4. 세 훅 비교 — 결제 시나리오로 한눈에

```
╔═══════════════════════════════════════════════════════════════════╗
```

## 5. useRef를 쓰면 안 되는 경우 vs 써야 하는 경우

```
useRef를 써야 하는 경우 (UI에 표시 안 되는 값):
  ✓ 멱등성 키 (서버 전송용, 화면에 안 나옴)
  ✓ 타이머 ID (setInterval, setTimeout)
  ✓ 이전 값 추적 (usePrevious 패턴)
  ✓ DOM 요소 참조 (input focus 등)
  ✓ 재시도 횟수 카운터

useState를 써야 하는 경우 (UI에 표시되는 값):
  ✓ 로딩 상태 (스피너 표시)
  ✓ 에러 메시지 (화면에 표시)
  ✓ 입력 폼 값
  ✓ 토글 on/off 상태

useMemo를 써야 하는 경우 (비싼 계산의 캐싱):
  ✓ 긴 리스트 필터링/정렬
  ✓ 복잡한 객체 파생 데이터
  ✓ 의존성 변경 시 자동 재계산이 필요한 경우

핵심 판단 기준:
┌─────────────────────────────────────────────────┐
│ "이 값이 바뀌면 화면이 바뀌어야 하나?"            │
│                                                 │
│   YES → useState                                │
│   NO  → useRef                                  │
│                                                 │
│ "이 값은 다른 값에서 파생되는 건가?"              │
│                                                 │
│   YES + 비싼 계산 → useMemo                     │
│   YES + 가벼운 계산 → 그냥 변수로 선언            │
└─────────────────────────────────────────────────┘
```

## 6. 전체 흐름 요약 — POS에서 결제까지

```
고객이 아메리카노 2잔을 장바구니에 담고 "결제하기" 클릭

프론트엔드                                    백엔드
─────────                                    ──────

1. generateIdempotencyKey(items)
   → "pos_a1b2c3_1707900000_x8k2m4n7"

2. useIdempotencyKey의 getKey()
   → keyRef.current에 저장
   → 같은 키를 반복 반환 가능

3. POST /api/orders
   Header: Idempotency-Key: pos_a1b2c3_...
   Body: { items: [...],
           idempotency_key: pos_a1b2c3_... }
                                              4. [Phase 8] IdempotencyMiddleware
                                                 → 키 조회 → 없음 → 핸들러 실행

                                              5. OrderService.create_order()
                                                 → Order 생성 (idempotencyKey 저장)
                                                 → 201 Created 응답

                                              6. [Phase 8] 응답을 IdempotencyRecord에 저장
                                                 → { key: "pos_a1b2c3_...",
                                                      statusCode: 201,
                                                      responseBody: "{...}",
                                                      expiresAt: +24h }

7. 응답 수신 → 성공
   → Toss 결제창 열기
   → reset() → keyRef.current = null
   (다음 주문 시 새 키 생성 준비)

─── 만약 시점 3에서 네트워크 에러가 나면? ───

3'. 재시도: getKey() → "pos_a1b2c3_..."  (같은 키)
    POST /api/orders (동일 요청)
                                              4'. IdempotencyMiddleware
                                                  → 키 조회 → 있음 + 미만료
                                                  → 저장된 201 응답 그대로 반환
                                                  → 핸들러 실행 안 함!

    → 주문 1개만 생성됨 ✓ (중복 없음)
```
