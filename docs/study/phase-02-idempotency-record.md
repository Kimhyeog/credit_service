# IdempotencyRecord란? — 같은 요청이 두 번 와도 한 번만 처리

> Phase 2 Step 2-1 IdempotencyRecord 모델 관련 설명

---

## 한 줄 요약

같은 요청이 중복으로 들어왔을 때, **두 번째부터는 실제 처리 없이 첫 번째 응답을 그대로 돌려주기 위한 "응답 저장소"**다.

---

## 상황 예시: 네트워크 불안정으로 같은 주문이 2번 전송됨

### 문제 상황

```
고객이 "결제하기" 클릭
     │
     ▼
POST /api/orders  ─────→  서버: 주문 생성 (o1, 9000원)
     │                          │
     │                          ▼
     │                     응답: 201 Created
     │                          │
     ✕  네트워크 끊김!           │
     │  (응답이 브라우저에       │
     │   도착하지 못함)          ▼
     │                     응답이 허공으로 사라짐...
     │
     ▼
브라우저: "응답이 안 왔네? 실패인가?"
     │
     ▼
자동 재시도: 같은 POST /api/orders 한 번 더 전송
     │
     ▼
서버: 주문 또 생성?? (o2, 9000원)  ← 💥 같은 주문이 2개!
```

고객은 1번만 주문했는데 **DB에 주문이 2개** 생긴다. 결제도 2번 될 수 있다.

---

### IdempotencyRecord가 해결하는 방법

```
고객이 "결제하기" 클릭
     │
     │  프론트엔드가 고유 키 생성: Idempotency-Key: "abc123"
     ▼

─── 첫 번째 요청 ───────────────────────────────────────────

POST /api/orders
Header: Idempotency-Key: abc123
     │
     ▼
서버 (미들웨어):
     │
     ├─ IdempotencyRecord 테이블에서 "abc123" 조회
     │  → 없음 (첫 요청)
     │
     ├─ 주문 생성 실행 → o1, 9000원
     │
     ├─ 응답을 IdempotencyRecord에 저장:
     │  ┌──────────────┬────────┬──────────────┬────────┬──────────────────┐
     │  │ idempotencyKey│ method │ path         │ status │ responseBody     │
     │  ├──────────────┼────────┼──────────────┼────────┼──────────────────┤
     │  │ abc123       │ POST   │ /api/orders  │ 201    │ {"id":"o1",...}  │
     │  └──────────────┴────────┴──────────────┴────────┴──────────────────┘
     │
     └─ 응답 반환: 201 Created {"id": "o1", ...}
            │
            ✕  네트워크 끊김! (응답 도착 실패)


─── 두 번째 요청 (재시도, 같은 키) ─────────────────────────

POST /api/orders
Header: Idempotency-Key: abc123      ← 같은 키!
     │
     ▼
서버 (미들웨어):
     │
     ├─ IdempotencyRecord 테이블에서 "abc123" 조회
     │  → 있다! (첫 번째 요청에서 저장해둔 것)
     │
     ├─ 주문 생성 실행하지 않음!     ← 핵심: 비즈니스 로직 스킵
     │
     └─ 저장된 응답을 그대로 반환: 201 Created {"id": "o1", ...}
            │
            ▼
       브라우저에 정상 도착!
```

**결과:** 주문은 o1 **딱 1개**, 고객은 정상 응답을 받음.

---

## IdempotencyRecord 테이블의 각 필드 역할

```
┌──────────────┬────────┬──────────────┬────────┬──────────────────┬─────────────────────┐
│idempotencyKey│ method │ path         │status  │ responseBody     │ expiresAt           │
│              │        │              │ Code   │                  │                     │
├──────────────┼────────┼──────────────┼────────┼──────────────────┼─────────────────────┤
│ abc123       │ POST   │ /api/orders  │ 201    │ {"id":"o1",...}  │ 2025-02-14 12:00:00 │
└──────────────┴────────┴──────────────┴────────┴──────────────────┴─────────────────────┘
  │               │        │              │         │                  │
  │               │        │              │         │                  └─ 24시간 후 만료
  │               │        │              │         │                     (무한히 쌓이지 않도록)
  │               │        │              │         │
  │               │        │              │         └─ 첫 번째 응답 본문 그대로 저장
  │               │        │              │            (두 번째 요청 시 이걸 꺼내서 반환)
  │               │        │              │
  │               │        │              └─ 첫 번째 응답의 HTTP 상태 코드
  │               │        │                 (201 Created, 400 Bad Request 등)
  │               │        │
  │               │        └─ 어떤 API 경로였는지
  │               │
  │               └─ 어떤 HTTP 메서드였는지
  │
  └─ 프론트엔드가 생성한 고유 키 (이걸로 "같은 요청인지" 판별)
```

---

## expiresAt이 왜 필요한가?

```
IdempotencyRecord 없이 (만료 없음):

  1월: abc123 저장
  2월: def456 저장
  3월: ghi789 저장
  ...
  12월: 레코드 수만 개 쌓임 → DB 용량 낭비, 조회 느려짐


expiresAt 있으면:

  abc123 저장 (expiresAt: 24시간 후)
       │
       │  24시간 경과
       ▼
  abc123 만료 → 미들웨어가 삭제
                 (같은 키로 새 요청이 오면 새로 처리)
```

24시간이면 네트워크 재시도가 충분히 끝나는 시간이다. 그 이후에 같은 키가 오면 새 요청으로 취급해도 안전하다.

## 전체 흐름 요약

```
프론트엔드                    미들웨어                         라우터
─────────                    ────────                         ──────

키 생성                   IdempotencyRecord
"abc123"                  테이블에서 조회
   │                          │
   │  POST + Key: abc123      │
   ├─────────────────────→    ├─ 없음 → 통과 ──────────→  주문 생성
   │                          │                              │
   │                          │         응답 저장 ←──────────┘
   │                          │         (key, 201, body)
   │  ←── 201 응답 ───────────┤
   │                          │
   │  (재시도)                │
   │  POST + Key: abc123      │
   ├─────────────────────→    ├─ 있음 → 저장된 응답 반환   (라우터 실행 안 함!)
   │                          │
   │  ←── 201 응답 (동일) ────┤
```
