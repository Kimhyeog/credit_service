# Payment?의 의미 — 왜 Optional인가

> Phase 2 Step 2-1 Order 모델의 `payment Payment?` 관련 설명

---

## 한 줄 요약

주문이 먼저 생성되고, 결제는 **나중에** 붙기 때문에 주문 생성 시점에는 결제 데이터가 없다. 그래서 `?`(optional)이다.

---

## 상황 예시: 주문 → 결제의 시간차

### 1단계: 고객이 "결제하기" 버튼을 누름

이 순간 **주문이 먼저 생성**된다. 아직 결제창은 안 열렸다.

```
[결제하기 클릭]
      │
      ▼
  POST /api/orders  →  Order 생성 (DB에 저장)
      │
      │  이 시점의 DB:
      │
      │  Order 테이블:
      │  ┌─────┬────────┬─────────┬─────────────┐
      │  │ id  │ status │ amount  │ payment     │
      │  ├─────┼────────┼─────────┼─────────────┤
      │  │ o1  │PENDING │ 9,000   │ null        │  ← 결제 아직 없음!
      │  └─────┴────────┴─────────┴─────────────┘
      │
      │  Payment 테이블:
      │  (비어있음)
      │
      ▼
  Toss 결제창 열림 (고객이 카드 정보 입력 중...)
```

**이 시점에서 Order는 존재하지만, Payment는 없다.** `payment`가 optional이 아니면(= 필수이면) 주문 생성 자체가 불가능해진다.

### 2단계: 고객이 결제창에서 승인

```
  [고객이 결제 승인]
      │
      ▼
  POST /api/payments/confirm  →  Payment 생성 (DB에 저장)
      │
      │  이 시점의 DB:
      │
      │  Order 테이블:
      │  ┌─────┬────────┬─────────┐
      │  │ id  │ status │ amount  │
      │  ├─────┼────────┼─────────┤
      │  │ o1  │ PAID   │ 9,000   │
      │  └─────┴────────┴─────────┘
      │
      │  Payment 테이블:
      │  ┌─────┬────────────┬────────┬─────────┐
      │  │ id  │ paymentKey │ status │ orderId │
      │  ├─────┼────────────┼────────┼─────────┤
      │  │ p1  │ pk_abc123  │ DONE   │ o1      │  ← 이제 연결됨!
      │  └─────┴────────────┴────────┴─────────┘
      │
      ▼
  주문 완료!
```

---

## 만약 optional이 아니면?

```prisma
# 이렇게 쓰면 (? 없이):
payment  Payment      # ← 필수! null 불가
```

```
주문 생성 시점:

  Order를 만들려면 Payment가 반드시 있어야 함
      │
      ├─ 그런데 Payment를 만들려면 Toss 결제창이 열려야 함
      │
      ├─ Toss 결제창을 열려면 orderId가 필요함
      │
      └─ orderId는 Order를 만들어야 나옴
          │
          └─ 🔄 순환! Order가 없으면 Payment 못 만들고,
                      Payment 없으면 Order 못 만든다
```

### 3단계: 결제를 안 하고 이탈한 경우

고객이 결제창에서 그냥 나가버리는 경우도 있다.

```
Order 테이블:
┌─────┬────────────────┬─────────┐
│ id  │ status         │ payment │
├─────┼────────────────┼─────────┤
│ o1  │ PAID           │ p1      │  ← 결제 완료된 주문
│ o2  │ PENDING        │ null    │  ← 결제 안 한 주문 (이탈)
│ o3  │ CANCELLED      │ null    │  ← 취소된 주문
└─────┴────────────────┴─────────┘
```

`payment`가 optional이기 때문에 이런 상황이 자연스럽게 표현된다. 결제 안 된 주문도 DB에 정상적으로 존재할 수 있다.

---

## 비교 요약

| 상황 | Order 존재 | Payment 존재 | `payment?`로 가능? |
|------|:---:|:---:|:---:|
| 결제하기 클릭 직후 | O | X | O |
| 결제창에서 이탈 | O | X | O |
| 결제 완료 | O | O | O |
| 주문 취소 | O | X | O |

`?`(optional) 하나가 "주문이 먼저, 결제는 나중"이라는 **비즈니스 흐름**을 DB 레벨에서 정확히 표현해주는 것이다.

---

## 부록: 일반 쇼핑몰 vs POS — 주문/결제 흐름 비교

### 일반 쇼핑몰 (배송지, 할인 등 입력이 있는 경우)

```
[상품 선택] → [장바구니]
                 │
                 ▼
         ┌──────────────────┐
         │ 배송지 입력       │
         │ 할인 쿠폰 적용    │
         │ 결제수단 선택     │
         └────────┬─────────┘
                  │
                  ▼
            [주문하기] 클릭
                  │
                  ▼
          Order 생성 (DB 저장)        ← Payment = null
          orderId = o1
                  │
                  │  (시간 차이 있음 — 바로 결제할 수도, 나중에 할 수도)
                  ▼
            [결제하기] 클릭
                  │
                  ▼
          결제창 열림 → 승인
                  │
                  ▼
          Payment 생성 (DB 저장)      ← orderId = o1 (FK 연결)
                  │
                  ▼
            주문 완료!
```

### 이 프로젝트 — 매장 POS (배송 없음, 현장 즉시 결제)

```
[메뉴 선택] → [장바구니]
                 │
                 ▼
            [결제하기] 클릭           ← 주문하기 + 결제하기가 하나의 버튼
                 │
                 ├─── ①  Order 생성 (DB 저장)       ← Payment = null
                 │        orderId = o1
                 │
                 ├─── ②  바로 Toss 결제창 열림       ← 끊김 없이 연속
                 │        고객이 카드 승인
                 │
                 └─── ③  Payment 생성 (DB 저장)      ← orderId = o1 (FK 연결)
                          │
                          ▼
                     주문 완료!
```

### 차이점

```
일반 쇼핑몰:    [주문하기] ──── 시간 차이 ──── [결제하기]
                    │                              │
                 Order 생성                    Payment 생성

POS:            [결제하기] 하나로 ①②③ 연속 실행
                    │
                 Order 생성 → 결제창 → Payment 생성
```

**DB에 기록되는 순서는 동일하다:**

| 순서 | 일어나는 일 | DB |
|:---:|---|---|
| 1 | Order 생성 | Order 행 생성, Payment = null |
| 2 | 결제 진행 | Toss 결제창에서 승인 |
| 3 | Payment 생성 | Payment 행 생성, `orderId = o1` (FK 연결) |

버튼이 하나든 둘이든, Order가 먼저 만들어지고 Payment가 나중에 붙는 구조는 같다. 그래서 `payment?`(optional)이 필요하다.
