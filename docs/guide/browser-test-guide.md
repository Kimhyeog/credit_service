## 2. POS 화면 테스트

**URL:** `http://localhost:3000`

### 2-1. 메뉴 표시 확인

1. 페이지 접속
2. **확인 항목:**
   - 상단바에 "Toss-Sync POS" 로고가 표시됨
   - 카테고리 탭(전체 / 커피 / 음료 / 베이커리)이 표시됨
   - 8개 메뉴 카드가 그리드로 표시됨 (이름, 가격)
   - 우측에 장바구니 영역이 표시됨 ("메뉴를 선택해주세요" 안내)

### 2-2. 카테고리 필터

1. "커피" 탭 클릭 → 아메리카노, 카페라떼, 바닐라라떼만 표시
2. "음료" 탭 클릭 → 녹차라떼, 초코라떼, 딸기스무디만 표시
3. "베이커리" 탭 클릭 → 크로와상, 치즈케이크만 표시
4. "전체" 탭 클릭 → 8개 모두 표시

### 2-3. 장바구니 조작

1. "아메리카노" 카드 클릭 → 장바구니에 "아메리카노 × 1" 추가
2. "아메리카노" 한 번 더 클릭 → 수량이 2로 증가
3. "카페라떼" 클릭 → 장바구니에 두 번째 항목 추가
4. **확인 항목:**
   - 합계 금액 = 아메리카노(4,500) × 2 + 카페라떼(5,000) × 1 = 14,000원
   - 항목 수가 정확히 표시됨
5. 수량 입력란을 직접 수정 → 금액이 재계산됨
6. 항목 옆 삭제 버튼(×) 클릭 → 해당 메뉴 제거
7. 모든 항목 제거 시 → "메뉴를 선택해주세요" 안내 복귀

### 2-4. 주문 모드 전환

1. 장바구니 하단에서 주문 모드 확인: "매장" / "포장"
2. "포장" 클릭 → 모드 전환됨 (TAKE_OUT)
3. "매장" 클릭 → 원복 (DINE_IN)

### 2-5. 네비게이션

1. 상단바에서 "키오스크" 링크 클릭 → `/kiosk`로 이동
2. 상단바에서 "KDS" 링크 클릭 → `/admin/orders`로 이동
3. 테마 토글 버튼(🌙/☀️) 확인

## 3. 키오스크 화면 테스트

**URL:** `http://localhost:3000/kiosk`

### 3-1. UI 확인

1. **확인 항목:**
   - "무엇을 주문하시겠어요?" 타이틀
   - 카테고리 탭 (전체 / 커피 / 음료 / 베이커리)
   - 메뉴 카드가 2열 그리드로 표시 (POS보다 큰 카드)
   - 하단 고정바: 장바구니 요약 + "주문하기" 버튼

### 3-2. 주문 플로우

1. 메뉴 2~3개 선택
2. 하단바에 항목 수와 합계 금액이 표시됨
3. "주문하기" 버튼 클릭 → 결제 진행 (섹션 5 참조)
4. 장바구니 비어있을 때 → "주문하기" 버튼 비활성화

## 4. 테이블 오더 테스트

**URL:** `http://localhost:3000/order/T1` (테이블 ID: T1)

### 4-1. UI 확인

1. **확인 항목:**
   - 상단에 "테이블 T1" 배지 표시
   - 메뉴가 리스트 형태로 표시 (그리드가 아닌 세로 목록)
   - 하단 고정바: 주문 모드 토글 + 금액 + "주문하기" 버튼

### 4-2. 테이블별 독립성

1. `/order/T1`에서 메뉴 선택
2. 새 탭에서 `/order/T2` 접속 → 장바구니 비어있음 (독립)
3. 각 테이블의 주문은 `table_id`가 다르게 저장됨

### 4-3. 주문 확인

1. 메뉴 선택 후 "주문하기" 클릭
2. 결제 완료 후 → `/order/T1`로 복귀
3. 관리자 페이지에서 해당 주문의 source가 "TABLE"로 표시됨

## 5. 결제 플로우 테스트

### 5-1. 실제 Toss 결제 테스트

> `NEXT_PUBLIC_PAYMENT_MOCK="false"` 설정 필요 (기본값)

1. POS(`/`)에서 메뉴 선택 후 "결제하기" 클릭
2. Toss 결제 팝업/리다이렉트 발생
3. **테스트 카드 정보:**
   - 카드번호: `4330-0000-0000-0880`
   - 유효기간: 미래 날짜 (예: `12/30`)
   - CVC: 아무 3자리 (예: `123`)
   - 비밀번호 앞 2자리: 아무 2자리 (예: `00`)

### 5-2. 결제 성공 확인

1. 테스트 카드로 결제 진행
2. `/payment/success` 페이지로 리다이렉트
3. **확인 항목:**
   - ✅ 체크마크 아이콘
   - "결제가 완료되었습니다" 메시지
   - 결제 금액, 결제 수단, 승인 시각 표시
4. "돌아가기" 클릭 → 원래 페이지(POS/키오스크/테이블오더)로 복귀

### 5-3. 결제 실패 확인

1. Toss 결제 팝업에서 "취소" 또는 결제 실패 유도
2. `/payment/fail` 페이지로 리다이렉트
3. **확인 항목:**
   - 에러 코드와 메시지 표시
   - "돌아가기" 버튼
4. "돌아가기" 클릭 → 원래 페이지로 복귀

### 5-4. 백엔드 상태 확인

결제 성공 후 터미널에서:
```bash
# 주문 상태 확인 (PAID)
curl http://localhost:8000/api/orders | python -m json.tool

# 결제 상태 확인 (DONE)
curl http://localhost:8000/api/payments/{orderId} | python -m json.tool
```

## 6. 관리자 대시보드 테스트

**URL:** `http://localhost:3000/admin`

### 6-1. 매출 요약 확인

1. 상단에 3개 카드 표시:
   - **오늘 매출** — PAID/PREPARING/COMPLETED 주문의 합계
   - **주문 건수** — 해당 주문의 개수
   - **평균 단가** — 매출 ÷ 건수
2. 결제 완료된 주문이 있으면 수치가 반영됨

### 6-2. 주문 목록

1. 주문 리스트가 최신순으로 표시
2. 각 주문 행에: 주문번호, 상태, 금액, 시간
3. 주문 클릭 → 우측에 주문 상세 패널 표시
4. **주문 상세 확인 항목:**
   - 주문 항목 (메뉴명 × 수량)
   - 결제 정보 (결제 키, 상태, 결제 수단)

### 6-3. 네비게이션

1. "KDS" 버튼 → `/admin/orders`로 이동
2. "POS" 버튼 → `/`로 이동

## 7. KDS (주방 디스플레이) 테스트

**URL:** `http://localhost:3000/admin/orders`

### 7-1. 칸반 보드 확인

4개 컬럼으로 주문이 분류됩니다:

| 컬럼 | 색상 | 상태 | 액션 버튼 |
|------|------|------|-----------|
| 접수 | 🔵 파랑 | PAID | "준비 시작" |
| 준비중 | 🟣 보라 | PREPARING | "완료" |
| 완료 | 🟢 초록 | COMPLETED | — |
| 취소 | 🔴 빨강 | CANCELLED / FAILED | — |

### 7-2. 상태 전환 테스트

**준비 과정:**
1. POS에서 메뉴 선택 → 결제 완료 (주문 상태: PAID)

**KDS 테스트:**
1. `/admin/orders` 접속
2. "접수" 컬럼에 새 주문이 표시됨
3. **확인 항목 (주문 카드):**
   - 주문번호 (예: #1)
   - 주문 시각 (HH:MM)
   - 메뉴 요약 (예: "아메리카노 x2")
   - 출처 배지 (POS / KIOSK / TABLE)

**PAID → PREPARING:**
1. "접수" 컬럼의 카드에서 "준비 시작" 클릭
2. 카드가 "준비중" 컬럼으로 이동

**PREPARING → COMPLETED:**
1. "준비중" 컬럼의 카드에서 "완료" 클릭
2. 카드가 "완료" 컬럼으로 이동

### 7-3. 실시간 업데이트

1. 브라우저 2개 열기: POS(`/`) + KDS(`/admin/orders`)
2. POS에서 주문 결제 완료
3. KDS에서 새 주문이 "접수" 컬럼에 자동 표시 (React-Query 자동 새로고침)

## 9. 엣지 케이스 테스트

### 9-1. 중복 탭 결제 방지

1. POS 탭 2개 열기 (탭 A, 탭 B)
2. 탭 A에서 메뉴 선택 → "결제하기" 클릭 (Toss 결제창 팝업)
3. 탭 B에서 메뉴 선택 → "결제하기" 클릭
4. **예상 결과:** 탭 B에서 결제가 차단됨 (다른 탭에서 결제 진행 중)

### 9-2. 오프라인 감지

1. 브라우저 개발자 도구 → Network 탭 → "Offline" 체크
2. **확인 항목:** 화면 상단에 "인터넷 연결이 끊어졌습니다. 연결을 확인해주세요." 배너 표시
3. 메뉴 선택 → "결제하기" 클릭
4. **예상 결과:** 결제가 차단됨 (오프라인 상태에서 결제 불가)
5. "Online" 복귀 → 배너 사라짐, 결제 가능

### 9-3. 멱등성 테스트 (동일 주문 중복 방지)

1. POS에서 동일한 메뉴 구성으로 빠르게 2번 "결제하기" 클릭
2. 백엔드에서 Idempotency-Key가 동일하면 첫 번째 응답을 반환
3. 동일 주문이 2번 생성되지 않음

### 9-4. 금액 불일치 방어

터미널에서 직접 테스트:
```bash
# 먼저 주문 생성
curl -X POST http://localhost:8000/api/orders \
  -H "Content-Type: application/json" \
  -H "Idempotency-Key: test_mismatch_key" \
  -d '{"items":[{"menu_id":"<메뉴ID>","quantity":1}],"idempotency_key":"test_mismatch_key"}'

# 틀린 금액으로 결제 시도
curl -X POST http://localhost:8000/api/payments/confirm \
  -H "Content-Type: application/json" \
  -d '{"payment_key":"pk_test","order_id":"<주문ID>","amount":99999}'
# → 400 "결제 금액이 일치하지 않습니다"
```

### 9-5. 결제 취소 테스트

1. 결제 완료된 주문의 ID 확인
2. 터미널에서:
```bash
curl -X POST http://localhost:8000/api/payments/{orderId}/cancel \
  -H "Content-Type: application/json" \
  -d '{"reason":"테스트 취소"}'
```
3. 결제 상태: DONE → CANCELED
4. 주문 상태: PAID → CANCELLED

### 9-6. 이미 취소된 결제 재취소

```bash
curl -X POST http://localhost:8000/api/payments/{orderId}/cancel \
  -H "Content-Type: application/json" \
  -d '{"reason":"재취소 시도"}'
# → 400 "CANCELED 상태의 결제는 취소할 수 없습니다"
```

## 10. 결제 복구 테스트

### 10-1. 미완료 결제 복구 시나리오

결제 중 브라우저 크래시를 시뮬레이션합니다:

1. POS에서 메뉴 선택 → "결제하기" 클릭
2. Toss 결제창이 뜬 상태에서 **브라우저 탭 강제 종료** (Ctrl+W 또는 탭 닫기)
3. 새 탭에서 `http://localhost:3000` 다시 접속
4. **확인 항목:**
   - 상단에 "미완료 결제 복구" 배너 표시
   - 자동 복구 결과: 서버에서 결제 확인 → "X건의 결제가 복구되었습니다"
   - 또는 수동 확인 필요 → "X건의 결제를 확인해주세요"

### 10-2. 복구 배너 닫기

1. 복구 배너의 "닫기" 또는 "확인" 클릭
2. 배너가 사라지고 정상 사용 가능

### 10-3. WAL 확인 (개발자 도구)

1. 브라우저 개발자 도구 → Application → Local Storage
2. `toss_sync_pos_wal` 키 확인
3. 결제 진행 중: WAL 엔트리에 상태(state)가 기록됨
4. 결제 완료 후: 해당 엔트리가 삭제됨

## 전체 테스트 시나리오 (End-to-End)

아래 순서로 전체 플로우를 통합 테스트할 수 있습니다:

### 시나리오 1: POS 결제 → KDS 처리

1. `/` 접속 → 아메리카노 2잔 + 크로와상 1개 선택
2. 주문 모드: "매장" 선택
3. "결제하기" → Toss 테스트 카드로 결제
4. 성공 페이지 확인 → "돌아가기"
5. `/admin/orders` 접속 → "접수" 컬럼에 주문 확인
6. "준비 시작" → "완료" 순서로 처리
7. `/admin` → 매출에 14,500원 반영 확인

### 시나리오 2: 키오스크 주문

1. `/kiosk` 접속 → 음료 카테고리 → 딸기스무디 선택
2. "주문하기" → 결제 진행
3. 결제 완료 → 키오스크 메인으로 복귀
4. `/admin/orders` → 출처 배지 "KIOSK" 확인

### 시나리오 3: 테이블 오더

1. `/order/T3` 접속 → 메뉴 선택 → "주문하기"
2. 결제 완료 → `/order/T3`로 복귀
3. `/admin/orders` → 출처 배지 "TABLE" 확인

### 시나리오 4: 주문 취소 (결제 전)

1. POS에서 주문 생성 (결제 팝업에서 취소)
2. 주문이 PENDING 상태로 남음
3. API로 취소:
```bash
curl -X PATCH http://localhost:8000/api/orders/{orderId}/cancel
```
4. 주문 상태: CANCELLED

### 시나리오 5: 다크 모드 전환 후 결제

1. 다크 모드 활성화
2. 키오스크(`/kiosk`)에서 주문 → 결제
3. 결제 성공/실패 페이지도 다크 모드로 표시됨
4. 모든 페이지가 일관된 테마 유지
